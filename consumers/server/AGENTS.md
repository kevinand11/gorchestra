# Server Consumer Package DOX

## Purpose

The `consumers/server/` package implements the v1 deployed Server Consumer: Nuxt browser app, Equipped Fastify API, authentication, Sessions, Workspace and Portfolio selection, Workspace Creation, Portfolio Creation, and Server-to-Core runtime assembly.

## Ownership

- `package.json`, `nuxt.config.ts`, and package-local TypeScript/Vitest config own Server Consumer package tooling.
- `src/` owns all package source code and is split by runtime boundary.
- `src/server/` owns server-only code: Equipped Fastify public runtime, Server-owned domain/storage, auth/session/selection, Workspace Creation, Portfolio Creation, and Core service assembly.
- `src/client/` owns Nuxt browser code: pages, middleware, composables, and app shell.
- `src/shared/` owns browser-safe cross-boundary contracts only; do not place server runtime, storage, Core, or secret-handling code there.
- `src/server/storage/` owns Server-owned JSON ORM schemas, migrations, and repo assembly; it must not contain Core Portfolio facts.
- `src/server/modules/` owns application use-case functions; API route handlers should stay thin adapters over these functions.

## Local Contracts

- Read `../../docs/consumers/CONTEXT.md`, `../../docs/consumers/server/CONTEXT.md`, and relevant Server Consumer ADRs before changing source behavior.
- Server-owned storage must not store Core Portfolio facts except Portfolio registry metadata and Core storage locations.
- Server-owned durable record ids and server-managed browser Session ids use Server Ids: lowercase monotonic Equipped ids generated through Server-owned helpers. Do not import Core id pipes/helpers to model Server Ids, and do not treat `coreStorageNamespace` as an id.
- Server-owned list endpoints generally return Server Consumer Paginated Query Envelopes ordered by the primary Server-owned record id descending unless a local route documents another primary record or intentionally bounded unpaginated selector list. `GET /api/workspaces` is the unpaginated Workspace/Portfolio selector hierarchy.
- Client code must not import from `src/server/`; server code may not import from `src/client/`; either side may import browser-safe types from `src/shared/`. The client route-contract Axios utility may import the Server API factory with `import type` only to derive Equipped Route Contracts; no runtime client-to-server imports are allowed.
- Portfolio-scoped API routes must validate the signed-in User, Selection Cookie, Active Workspace membership, and Portfolio registry ownership before opening Core; after Session authentication succeeds, missing or unusable selection must fail with Equipped `PreconditionRequiredError` / HTTP 428 so browser clients can redirect to `/select`.
- REST Portfolio authorization and Equipped socket identity resolution share one transport-neutral selected-Portfolio access resolver that validates the cache-confirmed Session first, then the Selection Cookie and current User, Workspace, Active Workspace membership, and Portfolio registry ownership. Equipped may accept the physical Socket.IO connection with no resolved identity; connection-time identity is a minimal non-authoritative routing snapshot, and every future registered socket path must revalidate its concrete current access.
- Reuse the Portfolio-scoped Server API context helper for Portfolio-scoped routes; it authorizes Session, Selection, Active Workspace membership, and Portfolio registry access before borrowing the runtime keyed by Portfolio Registry Entry id through a scoped callback. The borrow exposes only resolved Session/selection/access records plus the opened Core facade, contributes to in-flight drain accounting, and must not open or close Portfolio Core storage. An authorized unhealthy runtime fails with generic HTTP 503 Service Unavailable, never Selection Required or request-scoped Core fallback.
- Portfolio-scoped Project, Plan, Delivery, Repository, Secret, and Brain Memory UI/API routes use explicit Core command/query boundaries; add explicit Core operations before adding standalone Core routes for additional Portfolio facts. Portfolio API route definitions live under `src/server/api/routes/portfolio/` by entity, with `index.ts` bundling them under `/portfolio`. Brain Memory API routes are Portfolio-level under `/api/portfolio/memories`, not Project-nested. `GET /api/portfolio/memories` lists direct child Memories for a JSON `parentId` query defaulting to root. `GET /api/portfolio/memories/:memoryId` returns the selected Memory with revisions and direct children. `POST /api/portfolio/memories` creates a root or child Memory. `POST /api/portfolio/memories/:memoryId/revisions` appends content history using optimistic revision concurrency. Standalone Memory Link creation/archive routes are not exposed in this slice. Brain UI starts at `/brain`, with `/brain` reserved for Graph, `/brain/memories` serving the Memory hierarchy root with inline root Memory creation, and `/brain/memories/:memoryId` using canonical Memory detail URLs with inline current-content editing and inline child Memory creation. Repository API routes are nested under `/api/portfolio/projects/:projectId/repositories`, expose safe Repository config including `secretId`, and allow Active Workspace Members to list, view, create, and preflight Repositories. Plan API routes are nested under `/api/portfolio/projects/:projectId/plans`, and Active Workspace Members can list, view, and create Plans; Plan responses include the required `agentRunId` locator for the Planning Agent Run created with the Plan, while Agent Run details are read through `/api/portfolio/agent-runs/:agentRunId`. Delivery API routes are nested under `/api/portfolio/projects/:projectId/deliveries` and expose read-only materialized Delivery facts.
- Secret management requires `GORCHESTRA_SECRET_ENCRYPTION_KEY`, a base64/base64url value that decodes to exactly 32 bytes. Server Consumer Secret values are encrypted into inline protected value envelopes stored as Core Secret value refs; creation and value replacement preserve exact non-empty plaintext before protection. Server API responses expose redacted Secrets with Core Secret References and must never expose plaintext or protected value refs. Secret detail APIs allow metadata updates, value replacement, archive, and unarchive through selected-Portfolio authorization.
- `GET` routes must be read-only; do not refresh Sessions, set cookies, or mutate cache/storage from `GET` handlers.
- Server storage code must depend on the generic `ServerStorageAdapter` contract; adapter-specific imports belong only in adapter factory files.
- Server storage is opened and migrated once during application startup; module functions must not open, migrate, close, or implicitly resolve Server storage per operation. After migration, Portfolio Core Supervision must await one complete Portfolio Registry scan and runtime-start attempt before HTTP listening, record healthy/degraded state per Portfolio, and continue bounded-backoff retries for degraded runtimes without blocking healthy Portfolios.
- Module functions that need Server storage must receive it explicitly as `serverStorage`; module functions that need Server cache must receive it explicitly as `serverCache`; module functions that depend on time must receive an explicit `now` value.
- Workspace registry helpers may create and list Server-owned Workspace, Workspace Member, Workspace Owner role, and Portfolio Registry facts; Core Portfolio storage provisioning and Selection Cookie mutation belong in higher-level creation or selection modules.
- Core Portfolio storage assembly belongs under `src/server/core/`, must receive an explicit data directory at the boundary, and must keep adapter-specific imports in adapter factory files. Portfolio Core Supervision owns one process-local long-lived Portfolio Core Runtime keyed by Portfolio Registry Entry id, never `coreStorageNamespace`, for every registered Portfolio; the runtime contains that Portfolio's open storage, opened Core facade, notification publisher closed over the Portfolio id, and Dispatch Processor handle, while the namespace remains a deployment/storage detail. The provisional notifications publisher still logs the full Core-safe `{ portfolioId, notification }` value to the console; the Selected Portfolio Socket Connection is established, while Agent Run Channels and Notification delivery over them remain deferred.
- The Server Consumer Microsandbox adapter under `src/server/core/` implements Core's raw `consumer-managed` Sandbox Provider only; it bind-mounts each sandbox `/workspace` to a Server-owned host directory under the provided sandbox root, while runtime environment store semantics, `setEnv`, Secret redaction, output truncation, and release wiping stay in Core's managed sandbox wrapper.
- Portfolio Core Supervision discovers Portfolio Registry Entries through immediate new-entry signals plus periodic authoritative reconciliation; single-flights runtime generations by entry id under a bounded global startup limit; records ready/degraded state; retries degraded runtime startup indefinitely with capped exponential backoff and jitter; tracks scoped borrows for safe drain; starts, drains, stops, and restarts each runtime's Core Dispatch Processor; and provides authorized runtime lookup. Initial runtime readiness requires storage opening, Core preflight, and the processor's first authoritative scan; an initial processor failure retries a whole unpublished runtime generation, while a later processor-only failure leaves Core API borrows available and restarts only the processor. The Server supplies process-local Portfolio-scoped best-effort wake signaling and processor lifecycle configuration but must not select, coordinate, retry, or route Core Dispatch Requests; one failed Portfolio runtime must not suspend healthy Portfolios.
- Server Consumer config owns separate fully-resolved `portfolioCoreSupervision` and `coreDispatchProcessor` groups. Root environment parsing accepts deep-partial JSON overrides with defaults; supervision config includes 30-second registry reconciliation, a 1-second-to-60-second doubling retry with 20% jitter, a 60-second runtime-start timeout with stale-generation cleanup, a global startup concurrency default of four, and a 60-second total shutdown grace that must be at least the Core processor shutdown grace.
- Workspace Creation modules compose Server registry helpers without mutating Selection Cookies. Portfolio Creation modules compose Server registry helpers with Core Portfolio storage initialization; durable Portfolio Registry creation defines success and signals Portfolio Core Supervision immediately, while first runtime-start failure records degraded state for background retry rather than rolling registration back. Portfolio Creation must not mutate Selection Cookies or add API route behavior.
- Selection access modules validate signed-in User existence, Selection Cookie validity, Active Workspace membership, and Portfolio registry ownership; they must not mutate cookies, refresh Sessions, open Core, or add API route behavior. `/api/selection` remains the structured 200 Selection introspection endpoint; only missing or unusable selection uses HTTP 428 Selection Required, while authorized Portfolio runtime unavailability uses generic HTTP 503.
- API route handlers stay thin: parse with Valleyed pipes, define response and response-cookie pipes for API docs, translate cookies/body/status through Equipped request/response values, throw Equipped HTTP errors such as `NotAuthenticatedError` and `NotAuthorizedError`, and delegate business behavior to modules. Portfolio route responses must reuse exported Core query/domain result pipes rather than redefining Core DTO schemas; use narrow typed aliases only when needed to keep Equipped Route Contract declaration output serializable. Pure acknowledgement routes should return HTTP 204 No Content, list/read routes should avoid unnecessary wrapper objects, and state-introspection routes may keep explicit discriminators such as `authenticated` or `selected`.
- Equipped Router and Server registrations must preserve returned builder values so Route Contracts stay type-tracked; route factories should return one direct builder chain rather than breaking route registration into intermediate `withX` router variables, and nest/add one router at a time rather than using ignored mutations or variadic composition.
- Do not add browser/server DTO mirror files for Server API responses; client response types must flow from Equipped Route Contracts through `useServerApi()`, and named client types should derive from `ServerApi` method return types.
- Nuxt UI code lives under `src/client/` and must call the Server API through `src/client/composables/` client helpers rather than importing Server modules or Core code directly; use Axios for browser API requests. Import Vue framework APIs explicitly from `vue`; Nuxt APIs may use Nuxt auto-imports to keep source tests independent from Nuxt runtime imports.
- The browser Selected Portfolio Socket Connection is one private same-origin Socket.IO client using `/socket.io`, WebSocket-only transport, credentialed cookies, and no auth/query credential duplication. Explicit auth operations own its lifecycle: selected-route browser entry requires readiness within ten seconds; Session refresh and Selection replacement reconnect; logout, Selection clear, and HTTP auth/Selection loss disconnect; later network loss stays in selected UI while Socket.IO reconnects. SSR remains REST-only, the raw Socket.IO client is not exposed, and Agent Run-specific join/listen behavior is deferred.
- Nuxt page routes must use directory index files for route segments that also own children: use `x/index.vue` plus `x/y.vue`, not `x.vue` plus `x/y.vue`.
- Client styling uses Tailwind CSS v4 through the Vite plugin and CSS-first `@theme` tokens in `src/client/assets/css/main.css`; keep configurable visual values in semantic Tailwind tokens following the Stranerd-style naming pattern (`body`, `card`, `input`, `primary`, `secondary`, status colors, and `*-contrast`). Global base resets in `main.css` own box sizing, width containment, and text wrapping so form controls and long labels do not overflow narrow rails.
- Local UI components under `src/client/components/ui/` should be explicitly imported by pages/components by convention instead of relying on Nuxt component auto-imports. `UiSelect` is the shared searchable options-array select for single and multiple selection; pages should pass `options` rather than native `<option>` children.
- Feature-scoped reusable client components may live under `src/client/components/<feature>/`; they should compose feature composables with shared `Ui*` controls so pages do not duplicate fetch/form markup.
- Before adding or changing client form controls, buttons, labels, selects, textareas, or form wrappers, inspect `src/client/components/ui/` for an existing common component and use it. If an interactive session needs a generic UI component that does not exist yet, notify the user before proceeding; otherwise prefer creating or extending a shared `Ui*` component over page-local native control markup.
- Layout shell components must evaluate named slot presence in the render/template path; do not cache `$slots` / `useSlots()` presence checks in `computed()` because Vue slot objects are not reactive when async page data later adds or removes a slot.
- Test module functions directly with plain inputs and real storage/cache/Core wiring; do not test API endpoints or mock Equipped request/response values for this slice.

## Work Guidance

- Keep files focused and test service logic independently from route wiring.
- Use Equipped JsonCache-backed OTP and Session state; use Equipped JSON ORM for durable Server-owned state.
- In production/start/dev, Equipped Fastify owns the single public listener on `GORCHESTRA_PORT`; `/api/**` remains Equipped-owned, production/start delegates non-API fallback to the built Nuxt/Nitro Node listener, and dev delegates non-API fallback/HMR to a programmatic Nuxt dev runtime attached through Equipped's before-listen hook.
- Nuxt client navigation uses `/sign-in` for Email OTP authentication, `/select` for Workspace/Portfolio selection, Workspace Creation, and owner-only Portfolio Creation, `/projects` for selected-Portfolio Project state, `/projects/:projectId` redirects to Deliveries, `/projects/:projectId/deliveries` and `/projects/:projectId/deliveries/:deliveryId` for read-only materialized Delivery facts, `/projects/:projectId/plans`, `/projects/:projectId/plans/new`, and `/projects/:projectId/plans/:planId` for Plans with an embedded Agent Run surface loaded through the Plan's `agentRunId`, `/projects/:projectId/repositories/new` and `/projects/:projectId/repositories/:repositoryId` for Repository creation/detail, `/agent-run-profiles` for selected-Portfolio Agent Run Profile management, `/agent-run-profiles/new` for Agent Run Profile creation, `/agent-run-profiles/:agentRunProfileId` for Agent Run Profile editing and direct config references, `/secrets` for selected-Portfolio Secret state, and `/` as an auth/selection redirect landing route. Project-scoped tabs appear in the order Deliveries, Plans, Repositories, Config. The client app shell uses `src/client/components/layout/AppFrame.vue` plus `src/client/layouts/default.vue`, `portfolio.vue`, and `project.vue`; pages that need configurable topbar, left rail, or right rail content render `<NuxtLayout>` directly so named layout slots remain page-owned. Portfolio and Project layouts plug in scope defaults and forward optional right rails; the Project layout owns Project header fetching/loading/error state from its `projectId` prop, while child pages fetch Project data only when their own content needs it. Contextual creation actions stay in page or section toolbars rather than the global topbar.
- Client Session and Selection reads belong to the Query Cache as separate no-TTL entries; use plain auth/selection composables rather than a Pinia Session store. Use `useState`-backed composables for local client app state such as toasts; do not add Pinia stores. Pages register route guards explicitly with `definePageMeta`, using inline middleware for one-off page redirects and named middleware only for reusable guards. Route middleware must run in both Nuxt server and browser environments, read Session first, and read Selection only after authentication succeeds. Browser route guards may single-flight refresh a cached Session only when the cached Server Session response already has `refreshRecommended: true`; do not add local Session refresh timers or timestamp-derived refresh recommendations. Client API helpers must forward request cookies for server-side route checks.
- Page-load reads should use `useFetchAction` with a required string-array `queryKey` or function returning a string-array `queryKey`, plus `initialData`; `useFetchAction` returns readonly `data`, `isLoading`, `error`, `hasExecuted`, `execute`, and `reset`. The Server Consumer client uses a custom lightweight Query Cache rather than TanStack Query: Query Keys identify cached read data, dedupe in-flight work, hydrate per-request SSR data into the browser, support imperative route-guard reads, allow mutation responses to prime cached data, and support prefix invalidation with optional exact matching. Query Cache values must be JSON-serializable Server API response data. Fetch actions should return data and avoid local side effects; cache resource reads individually rather than as page-level setup bundles. Query data has no TTL and stays cached until explicit invalidation, clear, or page reload. Invalidation is fire-and-forget, stale-while-refetch, sets active fetch `isLoading`, ignores older in-flight results, and keeps stale data visible on refetch failures; initial no-data failures still throw into Nuxt route/error handling. User-triggered API calls should use `useApiAction`, keep failures local, and manually call `useQueryCache().invalidate(...)` or `set(...)` immediately after successful writes and before toast/navigation. Use `useQueryCache().clear(...)` for scope boundaries; clear never refetches, and `useFetchAction().reset()` only clears local loading/error state without deleting shared cached data. Portfolio-scoped Query Keys must include the selected Portfolio id; Portfolio cache is cleared on selection change/clear and browser HTTP 428 Selection Required; global auth-loss responses clear the entire Query Cache and redirect to `/sign-in`. Portfolio-scoped pages should use `useSelectedPortfolio()` after `has-selection` middleware instead of nullable selection checks. In-flight action dedupe must be scoped to the current Nuxt app/request rather than process-global state, and server-side `useServerApi()` must require an active Nuxt request context so SSR cookie-forwarding mistakes fail loudly. Browser `useServerApi()` must redirect HTTP 428 Precondition Required responses to `/select`, redirect HTTP 401/461 auth-loss responses to `/sign-in`, and still reject the original API call. Client Server API interactions should live in feature-grouped composables under `src/client/composables/` rather than page scripts; pages parse route params/query values into refs, call regular Vue composables with those refs, and keep rendering plus page-specific cross-feature computed state. Feature composables own their resource's `useServerApi()`, `useFetchAction()` / `useApiAction()`, Query Cache keys, cache invalidation, forms tied to mutations, and standard toasts; pages provide navigation through optional callbacks such as `onSuccess`. Destructure action-hook returns at declaration sites instead of retaining generic action objects solely to alias fields. Render user-triggered action loading and errors close to the invoking control; render subtle refresh indicators for cached reads when `isLoading && hasExecuted`. Toasts supplement local action UI; trigger success toasts explicitly from page/store code and keep user-action errors inline unless a global/non-local error toast is intentionally needed.
- Client forms that accept user input should use form draft classes under `src/client/forms/`, backed by `@gorchestra/form-draft`, with Valleyed rules, field errors, dirty/reset state, and `toModel()` conversion. Follow `libs/form-draft/README.md`: reusable form fragments used inside larger forms should be nested `FormDraft` classes; object fields whose subfields are edited should be nested drafts; item-edited arrays should use `FormDraftArray`; plain object/array fields are only for atomic whole-value replacement; optional single-select fields should use explicit `null` rather than empty-string sentinels; field rules should validate visible values without live transformers such as `v.asTrimmed()` or trim-based custom validators. Use `v.lazy()` for validation that depends on instance state instead of mutating a draft's rules in the constructor. Submit buttons must be disabled while their backing draft is invalid, not dirty when editing existing data, or the action is loading; submit handlers should call `draft.toModel()` and let `useApiAction()` catch validation throws rather than hand-rolling `if (!draft.valid) return` checks. Server route schemas remain authoritative for API validation.
