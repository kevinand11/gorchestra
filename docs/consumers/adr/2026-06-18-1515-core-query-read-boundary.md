# Core queries for Portfolio reads

Gorchestra Consumers read Core-owned Portfolio state through explicit Core domain queries rather than consumer-owned storage access, projections, or a generic resource-record API, superseding the narrower read boundary in [Core Orchestration API boundary](../../core/adr/2026-06-10-0208-core-orchestration-api-boundary.md). Consumer route handlers may expose Core command return values as mutation responses, but standalone or follow-up reads use Core queries. We chose this so Server Consumer UI and future consumers stay decoupled from Core storage layout and consistently use Core-owned derivations, accepting that Core will need a broader read/query surface for list, detail, and derived-state views.

The retained initial public query surface started with `listProjects`, which returns the Projects in the currently opened Portfolio without filters or pagination. `listProjects` returns Project records ordered by creation time and id, with each Project Source expanded into source-type-specific nested data owned by Core. For Source Control Projects, the expanded Project Source includes that Project's Repository records, ordered by creation time and id. `getProject` returns the same expanded Project shape for one Project. `listRepositories` and `getRepository` support Project-scoped Repository reads and validate that the Project exists before returning Repository data. `listPlans` and `getPlan` expose Project-scoped Plan records. `listDeliveries` and `getDelivery` expose read-only Project-scoped Delivery read models with materialized Delivery lifecycle fields, target Repository data, and ordered Slices. Future Project Source Types must define their own expanded query shape before they are exposed by Project or Delivery queries.
