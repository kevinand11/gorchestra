# Cache-confirmed JWT Sessions

The Server Consumer uses a signed JWT cookie for Sessions, containing the User id and normalized email label, and confirms validity through cache entries keyed by User. V1 permits one active Session per User: sign-in stores the current JWT in cache, authenticated requests verify both the JWT signature and cache match, and rolling refresh replaces the cached JWT when one day or less remains in the seven-day lifetime. Refresh immediately invalidates the previous JWT rather than accepting a grace token, preserving the invariant that only the current cache-confirmed Session JWT is accepted. Browser route guards may perform a single-flight refresh when a cached Session response already says refresh is recommended; long-lived tabs do not use local timers or timestamp recomputation to discover the refresh window. We chose this Stranerd-style cache-confirmed JWT cookie approach over opaque durable Session records so Session expiry and cleanup follow cache TTL while still allowing server-side invalidation.
