# Long-lived process-local Portfolio Core supervision

The Server Consumer owns one long-lived, process-local Portfolio Core Runtime for every Portfolio Registry Entry rather than opening and closing Core around each API request or Dispatch item. After Server storage migration, Portfolio Core Supervision completes one authoritative registry scan before HTTP listening; each runtime is keyed by the Portfolio Registry Entry id and contains open Portfolio storage, an opened non-owning Core facade, a Portfolio-scoped notification publisher, a best-effort Dispatch Wake service, and the Core Dispatch Processor handle. Authorized requests use scoped runtime borrows after access validation, so a missing or degraded runtime produces generic HTTP 503 without falling back to request-scoped Core.

New Portfolio registrations signal supervision immediately and periodic reconciliation recovers missed signals. Durable registration defines Portfolio Creation success even when the first runtime generation cannot become ready; unpublished generations fail independently and retry with capped exponential backoff, while healthy Portfolios continue. Initial readiness requires Core preflight and the processor's first authoritative scan. Once ready, a later processor-only failure leaves Core API borrows available because Dispatch Requests are durable, and supervision restarts only that processor.

The Server stops ingress before draining runtime borrows and processors, then closes Portfolio storage before Server infrastructure, with an overall configurable shutdown deadline. We chose eager per-process supervision over request-scoped or idle-evicted runtimes because persisted Dispatch work must resume without user traffic and runtime resources need one explicit owner; we rejected a deployment-global runtime owner because it would require leader election and proxying ordinary Core API calls between Server processes.
