# Dispatch coordination claims and Delivery work scheduling

Core Dispatch Requests use Dispatch Coordination Claims rather than Agent Run-only serialization keys. Each request may carry multiple claims, and a Consumer may run it only when every exclusive or shared-capacity claim can be acquired; this lets Delivery-level operations exclude all same-Delivery Slice work while sibling Slice operations can run concurrently within the `maxProcessableSliceSlots` capacity snapshotted from the Delivery Work Resolution that emitted them. Among acquirable readied requests, the v1 dispatcher prefers broader parent scopes before descendant scopes, with FIFO as the tie-breaker; blocked requests do not stall unrelated acquirable work.

Delivery work scheduling is split from concrete work: a Delivery Work Scheduler Pass reads current Delivery Context and local Delivery Work Resolution, emits concrete scheduler-actionable Delivery Work Operations, and later commands or completed operations request another scheduler pass. Provider-backed readiness checks belong to Process Delivery Work Operation because that boundary performs external side effects; if readiness fails there, it records failed Delivery preflight evidence, finishes the operation attempt, and requests another scheduler pass. Awaiting-review and failed Work States are not scheduler-actionable in this slice; Review Surface observation and manual retry/recovery remain future work. Operation jobs re-read current underlying state before side effects while ignoring only their own queued/started/finish dispatch Actions, and stale derived-state claims are successful no-ops. V1 records generic queued, started, and finished Delivery Work Dispatch Actions so schedulers can derive in-transit Delivery/Slice work and avoid duplicate scheduling; the queued Action and Core Dispatch Request are accepted in the same transaction, started Actions reference their queued Action, and finish Actions terminate each successfully handled attempt with either processed or stale-no-op outcome. Normal operation result Actions reference the started dispatch Action where practical. These Actions do not include lease recovery, and a generic durable Core Dispatch Request outbox remains a later reliability improvement.

V1 uses typed hierarchical claim scopes. Agent Run-related requests use exclusive `[agent-run, agentRunId]`. Delivery Work Scheduler Passes use exclusive `[delivery, deliveryId, scheduler]` so scheduler passes for one Delivery serialize with each other while still allowing Slice work to run. Delivery-level operations use exclusive `[delivery, deliveryId]`. Slice operations use a shared-capacity `[delivery, deliveryId, slice-pool]` claim with snapshotted capacity plus an exclusive `[delivery, deliveryId, slice, sliceId]` claim.
