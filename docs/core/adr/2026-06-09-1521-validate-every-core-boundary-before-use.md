# Validate every Core boundary before use

Core validates all data before trusting, storing, or deriving Portfolio behavior from it, regardless of whether the data arrives as a public Core Input, a Core Service Output, an external provider response, a provider/service exception, or a decoded Snapshot payload. TypeScript types and provider SDK types help author Core code but do not replace runtime validation at Core boundaries.

Public Consumer-to-Core APIs validate Core Inputs before core behavior runs and return `invalid-input` errors that carry validation detail instead of throwing. Command and query APIs use `CoreError`, while construction/import boundaries use narrower error unions such as `OpenCoreError` and `ImportSnapshotError` so their Result types do not promise unrelated domain failures. Core validation normalizes accepted boundary values where appropriate by projecting only known fields and ignoring unknown fields, so internal core logic can assume typed, normalized values without trusting extra data.

Each validation failure should preserve its fault domain: invalid Core Inputs are caller input failures, invalid Core Service Outputs are deployment service failures, invalid provider responses are external provider failures, and invalid Snapshot payloads are import compatibility or corruption failures. Core catches provider and Core Service exceptions at the boundary and converts them to safe Result errors or safe evidence. Core sanitizes provider, runtime, and service failure details before returning, storing, logging, publishing, or reusing evidence; raw external responses, headers, request bodies, exceptions, stack traces, and secret material are not exposed. We chose explicit boundary validation over trusting TypeScript, SDKs, services, or storage so Core-owned orchestration cannot be driven by malformed external data or leak unsafe diagnostics.
