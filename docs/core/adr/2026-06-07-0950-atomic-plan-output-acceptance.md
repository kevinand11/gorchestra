# Atomic Plan Output acceptance

Planning Agent Runs produce Plan Outputs as structured proposal shapes containing proposed new Deliveries with their initial Slices, new Memories with initial Memory Revisions, and new Memory Revisions for existing Memories, rather than directly mutating authoritative Portfolio graph state. A Plan Output is not itself a stored Portfolio artifact. Proposed Deliveries, Slice dependencies, Delivery dependencies, Memory creation roots, Memory creation children, and existing-Memory revisions use keyed record shapes where uniqueness belongs to the data shape rather than duplicate cleanup after parsing. Proposed Slices carry explicit contiguous `order` values because Slice order is domain-significant. A Plan Output does not add Slices to an existing Delivery; follow-on work is represented as a new Delivery that may depend on an existing Delivery or another proposed Delivery in the same Plan Output through a `depends-on` Link. Slice-level dependencies stay within one Delivery and materialize as Slice-to-Slice `depends-on` Links. A Plan Output does not propose arbitrary Core Links; accepting it derives produced Links for materialized Memories and Memory Revisions and depends-on Links for Delivery or Slice dependencies. A Plan Output is accepted or rejected as a whole: accepting it materializes all proposed artifacts atomically, including Instruction Sources stored on the materialized Slices, while rejecting it materializes none of them. Pure structural invariants such as non-empty output, contiguous Slice orders, known same-output dependency keys, self-dependency rejection, and proposed dependency cycle rejection belong in the Plan Output proposal pipe so invalid tool calls are refused before proposal events are recorded. Storage-dependent checks such as target Repository existence, same-Project existing Delivery dependencies, existing Memory parents, and Memory Revision freshness remain acceptance-time checks. Stale or no-op proposed Memory Revisions reject the whole Plan Output rather than partially materializing non-conflicting parts. Materialization uses deterministic ordering: Deliveries by proposed Delivery key, Slices by ascending order, Memory creation siblings by proposed Memory key, existing-Memory revisions by Memory id, and Links grouped as Delivery depends-on, Slice depends-on, Plan-to-Memory produced, then Plan-to-MemoryRevision produced. If only part of one output is acceptable, the Planner negotiates with the intelligence behind the Agent Run until a new acceptable whole is produced. The Plan remains reusable and may produce more Plan Outputs later; separate outputs can intentionally materialize different acceptable chunks over time, such as durable Memory changes before later Delivery and Slice proposals.
