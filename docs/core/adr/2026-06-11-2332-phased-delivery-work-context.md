# Phased Delivery Context

Superseded in part by [Dispatch coordination claims and Delivery work scheduling](./2026-07-04-2022-dispatch-coordination-claims-and-delivery-work.md), which replaces the monolithic `scheduleDeliveryWork` worker-pool direction with dispatch-coordinated Delivery scheduler passes and concrete Delivery Work Operations.

Delivery queries and commands prepare a transient Delivery Context instead of independently reloading and reinterpreting required Portfolio facts. Delivery Context contains scoped validated Portfolio facts needed to derive Delivery and Slice Work States for one Delivery; the Work States are derived from the context and are not fields on the context. The context stores at most one Delivery Artifact as a singular field, stores each Slice with its optional Slice Artifact and direct Slice dependency links, and provides Delivery Actions sorted by performed time so downstream derivation can preserve ordering without resorting. Delivery Context does not include Delivery Work Resolution, selected Model records, selected Model Provider records, or provider access plaintext.

Delivery Work Resolution is resolved separately for scheduler-actionable Delivery work. It contains the resolved Delivery Config and selected execution Model identity needed for a scheduler pass, but not provider access plaintext. Secret plaintext is resolved only on demand by provider-family façades for the specific preflight or external operation that needs it, and must not be written to Actions, Artifact records, logs, or other durable facts.

Superseded dispatch-coordination work moved provider-backed readiness from the scheduler pass into Process Delivery Work Operation. Delivery Work Resolution still resolves required config or returns failed Delivery preflight checks for user-fixable readiness such as missing, inactive, unresolved, or archived readiness dependencies. Provider preflight then resolves provider access on demand, evaluates the resolved Repository and Model readiness inputs, and returns validation checks before concrete operation side effects. Non-actionable states such as closed, unqueued, dependency-blocked, preflight-failed, and ready-to-ship do not require Delivery Work Resolution.

Provider calls that mutate external systems still happen outside storage transactions. A scheduleDeliveryWork pass writes Actions or Artifact records from the Delivery Context, Delivery Work State, Delivery Work Resolution, and operation claim it read at the start of the pass; later configuration or state changes apply to later passes. The scheduler or consumer runtime must ensure only one worker processes a Delivery at a time, so scheduleDeliveryWork does not perform a second Delivery Context rebuild or freshness-fingerprint comparison after provider calls.

For Slice work, scheduleDeliveryWork follows a worker-pool style drain loop. It fills up to `maxProcessableSliceSlots` concurrent in-call Slice operation slots, refetches Delivery Context as slots open, and continues until no actionable Slice work remains. Slots are occupied while scheduleDeliveryWork is actively processing a Slice operation, such as creating a Slice Artifact, running or reusing an Agent Run through runner completion, validating a Slice Artifact, or validating a promoted Slice against the Delivery Artifact. Incomplete Agent Runs are transient runtime/adoption facts rather than public Slice Work States in v1. v1 does not impose a separate total-claims-per-call cap.

scheduleDeliveryWork returns a single success summary rather than worked/no-op variants. The summary includes `processedCount`, incremented for every claimed Delivery-level or Slice-level operation attempt, and `failures`, a non-fatal failure list with scope, operation, and safe summary. Storage failures, invalid Core Service Outputs, invariant violations, and other whole-loop operational failures still return operation errors.

In the near term, the scheduler or consumer runtime must ensure only one worker processes a Delivery at a time.
