# Phased Delivery Context

Delivery queries and commands prepare a transient Delivery Context instead of independently reloading and reinterpreting required Portfolio facts. Delivery Context contains scoped validated Portfolio facts needed to derive Delivery and Slice Work States for one Delivery; the Work States are derived from the context and are not fields on the context. The context stores at most one Delivery Artifact as a singular field, stores each Slice with its optional Slice Artifact and direct Slice dependency links, and provides Delivery Actions sorted by performed time so downstream derivation can preserve ordering without resorting. Delivery Context does not include Delivery Work Resolution, selected Model records, selected Model Provider records, or provider access plaintext.

Delivery Work Resolution is resolved separately for scheduler-actionable Delivery work. It contains the resolved Delivery Config and selected execution Model identity needed for a scheduler pass, but not provider access plaintext. Secret plaintext is resolved only on demand by provider-family façades for the specific preflight or external operation that needs it, and must not be written to Actions, Artifact records, freshness fingerprints, logs, or other durable facts. Freshness checks use operation-scoped fingerprints derived from non-secret stored facts and resolved non-secret work inputs.

Provider-backed readiness still runs before scheduler-actionable work, but it is separate from Delivery Context construction. Delivery Work Resolution resolves required config or returns failed Delivery preflight checks for user-fixable readiness such as missing, inactive, unresolved, or archived readiness dependencies. Provider preflight then resolves provider access on demand, evaluates the resolved Repository and Model readiness inputs, and returns validation checks. Non-actionable states such as closed, unqueued, dependency-blocked, preflight-failed, and ready-to-ship do not require Delivery Work Resolution. Scheduler-actionable states resolve Delivery work and run provider preflight before handler dispatch, even when a handler is not yet implemented, so readiness semantics remain consistent.

Provider calls that mutate external systems still happen outside storage transactions. After a provider call, Core rebuilds or rechecks the relevant context facts inside a write transaction and writes Actions or Artifact records only if the operation-scoped freshness fingerprint still matches. Stale provider results return claim-conflict no-ops and do not become authoritative Core history.

For Slice work, runDeliveryWork follows a worker-pool style drain loop. It fills up to `maxProcessableSliceSlots` concurrent in-call Slice operation slots, refetches Delivery Context as slots open, and continues until no actionable Slice work remains. Slots are occupied while runDeliveryWork is actively processing a Slice operation, such as creating a Slice Artifact, running or reusing an Agent Run through runner completion, validating a Slice Artifact, or validating a promoted Slice against the Delivery Artifact. Incomplete Agent Runs are transient runtime/adoption facts rather than public Slice Work States in v1. v1 does not impose a separate total-claims-per-call cap.

runDeliveryWork returns a single success summary rather than worked/no-op variants. The summary includes `processedCount`, incremented for every claimed Delivery-level or Slice-level operation attempt, and `failures`, a non-fatal failure list with scope, operation, and safe summary. Storage failures, invalid Core Service Outputs, invariant violations, and other whole-loop operational failures still return operation errors.

In the near term, the scheduler or consumer runtime must ensure only one worker processes a Delivery at a time. Core still uses operation-scoped freshness checks around external provider mutations to avoid stale writes.
